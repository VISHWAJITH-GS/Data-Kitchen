Here are 10 self-contained build prompts, one per module, sequenced so each builds on the last. Feed them to your coding assistant (or Claude Code) in order.

---

**Prompt 1 — System Core & Wasm Pipeline**
"Set up the base React + Vite + TypeScript project for a browser-based data prep tool called Data Preparation Studio. Initialize DuckDB-Wasm running inside a dedicated Web Worker (not the main thread), with a typed message-passing contract between the UI and the worker (e.g. `INGEST`, `PROFILE`, `TRANSFORM`, `PREVIEW`, `EXPORT` message types with request/response IDs for correlating async replies). Add memory safeguards: detect file size on drop, warn above ~100MB, and guard against out-of-memory conditions in the worker with try/catch and a graceful error message posted back to the UI. Do not implement any UI yet beyond a minimal file-drop test harness to confirm the worker boots and DuckDB-Wasm initializes correctly."

**Prompt 2 — Data Model & Schema Engine**
"On top of the DuckDB-Wasm worker pipeline, implement ingestion for CSV and Parquet files that registers the uploaded file as an immutable base table in DuckDB (never mutated in place). Build a type-sniffing routine that inspects each column and infers data type (string, integer, float, boolean, date-like), plus column metadata: name, position, null count, distinct count, and inferred semantic hints (e.g. looks like a date, looks like an email). Store this metadata in a typed schema object returned to the main thread. Keep the original ingested table as the permanent baseline state, separate from any derived/transformed views."

**Prompt 3 — Recipe Engine & SQL Compiler**
"Implement the Recipe Engine: a declarative model where every user transformation (remove duplicates, fill nulls, standardize dates, trim whitespace, rename column, etc.) is stored as a serializable recipe step object (type, target column(s), parameters). Write a compiler that takes the ordered list of recipe steps and the baseline table and dynamically generates a single SQL view (or chained views) in DuckDB representing the current transformed dataset — never mutating data directly. Support undo (pop last step and recompile), and deleting/disabling an arbitrary step in the middle of the list with automatic recomputation of all subsequent steps."

**Prompt 4 — Data Health & Profiling Architecture**
"Build a two-pass profiling engine using DuckDB SQL queries: pass one computes cheap aggregate stats (row count, column count, null counts per column, duplicate row count); pass two runs more targeted heuristics (whitespace anomalies, inconsistent types within a column, malformed/ambiguous date formats). Convert results into prioritized 'issue' objects (issue type, affected column, severity, human-readable description, suggested fix). Implement a weighted 0–100 health score calculated from four sub-scores: completeness, uniqueness, consistency, and structural validity, with critical issues weighted more heavily than cosmetic ones."

**Prompt 5 — Interactive Grid Integration**
"Integrate AG Grid Community as the central spreadsheet view, backed by the current recipe-compiled DuckDB view (not the whole dataset in memory). Implement viewport-based lazy loading: as the user scrolls, request only the visible row range from the worker via `PREVIEW` messages, using DuckDB LIMIT/OFFSET or equivalent chunked queries. Ensure the grid re-queries and refreshes automatically whenever the recipe changes (a step is added, undone, or edited). Support inline column header renaming with validation against duplicate or invalid identifiers, wired back into the recipe engine as a rename step."

**Prompt 6 — Guided Transformation UI/UX**
"Build the diagnosis/action panel that renders the issues from the profiling engine as plain-language issue cards (e.g. '54 empty prices found' rather than 'missing-value imputation'), each with one or more suggested one-click fixes. For ambiguous cases (e.g. ambiguous date formats like 04/05/2023), show a decision dialog forcing an explicit user choice instead of silently guessing. Applying a fix should push a new step into the Recipe Engine and refresh the grid and health score. Also build the recipe/history panel showing each step in plain language (e.g. 'Step 3 — Removed 312 duplicate rows') with per-step undo/delete controls."

**Prompt 7 — Export Pipeline & Data Integrity**
"Implement export functionality that takes the current fully-compiled recipe view in DuckDB and serializes it in-memory to CSV and Parquet formats, triggering a local browser download (no server round-trip). Handle large-result serialization without blocking the UI thread (perform it in the worker). Add safeguards: warn if exporting would exceed a safe in-memory size, verify row/column counts match expectations before completing the export, and clearly communicate in the UI whether the export is a new file or would overwrite the original."

**Prompt 8 — Resilience, Edge Cases & Error Boundaries**
"Harden the application against failure modes: malformed or corrupt CSV files, mismatched delimiters, files exceeding memory budgets, DuckDB-Wasm query failures, and worker crashes. Never surface raw engine/SQL error text to the user — map all failure types to clear, non-technical error states with actionable next steps (e.g. 'This file couldn't be parsed as CSV — check that it uses consistent commas'). Implement worker restart/recovery logic so a single failed operation doesn't require a full page reload, and add React error boundaries around the grid and action panel so a UI-level crash doesn't take down the whole app."

**Prompt 9 — Build, Headers & Deployment Strategy**
"Configure the production build and static hosting setup: set Cross-Origin-Opener-Policy and Cross-Origin-Embedder-Policy headers correctly (for the chosen host, e.g. Vercel/Netlify/Cloudflare Pages config files) to support DuckDB-Wasm's multi-threaded mode via SharedArrayBuffer, with a fallback to single-threaded mode if headers aren't available. Optimize the bundle (code-splitting the DuckDB-Wasm and AG Grid chunks, lazy-loading non-critical UI). Audit and document a 'zero-leak privacy' checklist: confirm no analytics, error reporting, fonts, or other third-party requests transmit dataset contents or metadata off-device."

**Prompt 10 — End-to-End Implementation Blueprint**
"Assemble all previous modules (worker/DuckDB core, schema engine, recipe engine, profiling, AG Grid, guided UI, export, resilience, deployment config) into a complete working V1 application matching this scope: upload CSV/Parquet → automatic profiling and health score → prioritized issue cards with guided one-click fixes and ambiguity dialogs → live-updating grid via viewport queries → recipe/history panel with undo → export to CSV/Parquet. Produce a verification checklist covering each success metric (time-to-first-diagnosis, workflow completion without docs, undo/recovery correctness, export correctness, responsiveness under large files) and a phased release roadmap from V1 scope to the future-expansion features (saved recipes, quality rules, SQL expert mode, local persistence)."
